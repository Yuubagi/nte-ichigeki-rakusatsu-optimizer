# 詳細(仕組み・確認内容・制限事項など)

[README](../README.md) に入れていない、技術的な内容をまとめています。

## 計算の仕組み

盤面にアイテムを重ならないように置く問題なので、単純な足し算では解けません。次の段階で計算します。

1. **形状を考えない上限を求めます。** アイテムの形を無視して、「マス数の合計」と「個数」だけを制限にしたときの最大値を、動的計画法で厳密に求めます。実際の配置の収益は、これを超えません。
2. **良い配置を作ります。** 盤面の左上から順に「ここから置く/置かない」を決めていく探索を、有望な候補だけに絞りながら進めます(ビームサーチ)。
3. **個数の組み合わせから調べます。** 上の上限で有望な「アイテムごとの個数の組み合わせ」を順に取り出し、その個数で実際に盤面へ収まるかを探索で確かめます。
4. **一部を置き直して改善します。** 今の配置の一部(四角い範囲や帯状の範囲)を外し、空いた場所を探索で置き直します。改善が止まったときは、別の形から探し直します。

計算はWeb Workerで行うため、計算中も画面は固まりません(Workerが使えない環境では、そのまま計算します)。

## 「最適」の意味と限界

次のどちらかを満たしたときだけ「最適です」と表示します。

- 見つけた配置の収益が、形状を考えない上限と一致した。
- 上限を超える可能性のある個数の組み合わせを、残らず調べ、どれも盤面に収まらないことを確認できた。

10秒以内にどちらも満たせなかったときは、見つかった最良の配置を表示し、最適との差が最大でいくつかを示します(上の上限と、表示している配置の差です)。この場合は**最適とは限りません**。

## 確認したこと

開発中に、次の確認をしました。確認に使ったスクリプトは、このリポジトリには含めていません。

- **専用のソルバーとの比較。** 所持数をランダムに変えた40通りの条件(16種類のアイテム、盤面は縦8×横15、個数の上限は99)で、SciPyの`scipy.optimize.milp`(HiGHS)を使い、整数計画として解いた最適値と、このツールの結果を比較しました。全40件で値が一致しました。40件中31件は「最適」と表示され、残りの9件は10秒以内に最適と証明できませんでしたが、値は一致していました。
- **配置の妥当性。** 出力された配置が、重なりがなく、盤面からはみ出さず、所持数と個数の上限を守っていることを、上の全件で確認しました。
- **アイテムを増やした場合。** ランダムなアイテムを最大300件まで増やして計算し、どれも10秒程度で終わり、メモリの使用量も、Node.jsでの測定で約260MB以下でした。
- **画面の動作。** Chromiumの自動操作で、入力、計算、中止、盤面と内訳の表での選択、貼り付け、書き出し、画面幅320〜1920pxでの表示(横にはみ出さないこと)、ダークモードを確認しました。入力欄を保存する領域(localStorage)が使えない場合、保存データが壊れている場合、Web Workerが使えない場合、盤面に入らないアイテムや不正な入力がある場合、画像が読み込めない場合、通信量を抑える設定の場合でも、エラーにならず動くことを確認しました。

これは、特定の条件での確認です。すべての入力での正しさを保証するものではありません。

## 制限事項

- 盤面は縦8×横15の欠けのない長方形で、配置できる個数は最大99個で固定です。アイテムは回転しない長方形のみです。
- 隣り合うアイテムによるボーナスなど、ゲーム内のその他の効果は考慮しません。
- 計算時間は10秒の固定です。条件によっては、最適と証明できないことがあります。
- 同じ収益になる配置は複数あるため、表示される配置は、その1つです。
- ゲームの仕様変更などで、実際の結果と異なる場合があります。
- 最近のブラウザを想定しています。動作を確認したのはChromiumのみです。

## 画像

画像はすべて飾りで、なくても、すべての機能と情報は同じように使えます。環境によって体験に差が出ないように、次の作りにしています。

- 通信量を抑える設定(データセーバーなど)のときは、どの画像も読み込みません。
- ページ上部の画像は、画面幅に合う1枚だけを読み込みます(WebPが使えない環境では、JPEGを読み込みます)。読み込めないときは、盤面のマス目をイメージした背景になります。タイトルの文字は、画像の暗い部分に重ねて、白い文字が読めるコントラストを保っています。
- 盤面のアイテム画像(`img/board/`)は、置かれたアイテムの分だけ読み込みます。読み込んでいる間は、画像の枠と同じ色の四角を表示します(文字の表示から画像に切り替わって見えないようにするため)。表のアイコンは、通信の回数を減らすため、1枚の画像(`img/icons.webp`)にまとめています。
- アイテムの画像は、橙品質39種類に、名前で対応づけています(前後のかぎかっこ「」は無視します)。対応する名前以外の行には、画像は付きません。
- 画像がない(または読み込めない)アイテムは、アイテムごとの色の四角で表示します。盤面では、名前が枠に収まるとき(縦1マスは1行、2マス以上は最大2行)だけフルネームを、収まらないときは名前の1文字目を重ねます。表と内訳の表のアイコンは、1文字目です。
- 盤面の画像には、名前の文字を重ねません。フルネームは、盤面のアイテムを選んだときの説明、内訳の表、`title` で確認できます。

## 公開URLに依存する設定

SNSで共有されたときの表示(OGP)には、公開ページのURLを直接書いています(`index.html` の `og:url` と `og:image`)。リポジトリ名やアカウント名を変えて、公開URLが変わったときは、この2か所を直してください。

## 橙品質の全アイテムプリセット

`index.html` の `ALL_ORANGE_ROWS` に、2026年11月13日時点の[NTE一撃落札DB](https://ddangcalc.com/ja/items)の橙品質39種類を収録しています。名前と縦横は一覧の公開データ、展示収益は各アイテム詳細ページの「陳列棚の1時間あたり収益」を確認しました。売却価格に一定の係数を掛けて推算してはいません。

「アイテム一覧」と「所持アイテム」の2つのタブで管理します。一覧の追加ボタンを押すと、所持アイテムに所持数1で追加します。名前の前後の空白と、外側のかぎかっこ「」『』は同一視し、追加済みの場合は既存行の所持数を1増やします。一覧にも現在の所持数を表示し、所持アイテムタブで数を直接編集した場合も反映します。既存行の収益・寸法は変更しません。空欄（無制限）や数値でない所持数の行に追加した場合は、所持数1として数え始めます。所持アイテムから削除すれば、再び追加できます。計算・一括貼り付け・書き出しの対象は所持アイテムです。新規利用時の所持アイテムは空です。

保存キーは従来の `exhibit-optimizer-v2` を引き継ぎ、`inventory: true` で新形式を区別します。旧形式から初回移行するとき、プリセットと名前・収益・寸法が一致し、所持数が0の行だけを省きます。正の所持数、空欄（無制限）、変更済みの値、独自アイテムは保持します。新形式への移行後は、所持数0の行も通常どおり保存されます。「すべて削除」は確認ダイアログの後に所持アイテムを空にします。

プリセットはHTMLに同梱され、読み込み時に出典サイトへ接続する必要はありません。橙品質39種類の画像を同梱し、表・内訳・盤面で表示します。追加17種類の画像は[NTE一撃落札DB](https://ddangcalc.com/ja/items)の各アイテム画像から取得し、WebPとアイコン用スプライトに変換しました。画像・名称などのゲーム内コンテンツの権利はHotta Studioに帰属します。ゲームや出典の更新で値が変わった場合は、プリセットの更新が必要です。
